# data/sampled

Generated by `npm run data:build` (`scripts/build-requirements.ts`) from `data/raw/XMLZIPFile/*.xml` (PURE dataset subset, 18 documents). Do not edit these files by hand: change the script and rebuild.

| File | Content |
|---|---|
| `requirements.csv` | 126 sampled candidate requirements (dataset v0.1) |
| `candidates-all.csv` | All 2,686 extracted candidates, before sampling |
| `../annotations/annotation-template.csv` | One empty annotation row per sampled requirement (fields from plan M1.5) |

## Columns of `requirements.csv`

| Column | Meaning |
|---|---|
| `requirement_id` | `R001`… unique, ordered by document and position |
| `source_document` | XML file name in `data/raw/XMLZIPFile` |
| `source_section` | Section number and title in the source document (empty if the source has none) |
| `source_req_id` | Original requirement ID in the source (`<req id>`, `REQ-n`, `[SSSnnn]`), empty if none |
| `requirement_text` | Original wording; only whitespace is collapsed, PDF ligatures expanded and ID labels removed |
| `context_before` / `context_after` | Previous / next text unit in the **same section** (max 300 chars) |
| `related_requirement_ids` | Other sampled requirements taken from the same section (`;`-separated), so that potential inconsistency can be checked |
| `target_diagram` | `USE_CASE` / `CLASS` / `SEQUENCE`, **heuristic draft, must be reviewed** (see below) |
| `source_type` | `REAL` for every row (no synthetic data in this file) |

## How candidates were extracted

- Documents with `<req>` tags (cctns, gamma j, eirene_fun, ertms, keepass, peering): each `<req>` is one candidate.
- Other documents: sentences containing `shall / must / should / is required to / has to`; for documents with fewer than 10 such sentences (get real, video search, …) `will / can` are accepted too. TCS is split on its `[SSSnnn]` tags.
- Excluded: fewer than 5 or more than 70 words, statements about the document itself, leftover IEEE template guidance, list lead-ins whose items are elsewhere ("… the following:"), EIRENE informative clauses `(I)`, introductory sections (purpose, scope, references, user classes, …), and duplicates within a document.

## Sampling

Deterministic (seed `392`): 7 requirements per document, so no single domain dominates (eirene_fun alone holds ~15% of all candidates). Inside a document, runs of 1–3 consecutive requirements from the same section are drawn; 59/126 rows belong to such clusters. Length: 6–61 words, median 18.

## Known limitations (Member 1 to review before freezing v0.1)

1. **`target_diagram` is a keyword heuristic** (interaction verbs → SEQUENCE, data/structure verbs → CLASS, otherwise USE_CASE). The current split is 107 USE_CASE / 11 SEQUENCE / 8 CLASS, which is too skewed. Re-assign manually where needed.
2. Many sampled rows are non-functional or project constraints (performance, platform, legal). They are real, but some have no meaningful UML target; decide whether to keep or replace them.
3. Some candidates are not requirements in the strict sense: peering `<req>`s are use-case pre/post-conditions, and get real / video search are informal student documents. Candidates are not labels: annotators decide.
4. PDF conversion errors stay in the text on purpose (e.g. "u nits", "can' mt ove"), because the original wording must not be rewritten.

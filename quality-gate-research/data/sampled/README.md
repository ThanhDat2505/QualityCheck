# data/sampled

Generated by `npm run data:build` (`scripts/build-requirements.ts`) from `data/raw/XMLZIPFile/*.xml` (PURE dataset subset, 18 documents). Do not edit these files by hand: change the script and rebuild.

| File | Content |
|---|---|
| `requirements.csv` | 120 sampled candidate requirements (dataset v0.1 draft) |
| `candidates-all.csv` | All 2,686 extracted candidates (with context), before sampling. When replacing a sampled row, do **not** pick a text already used in `data/fixtures/smoke.csv` |
| `target-diagram-overrides.csv` | Manual `target_diagram` decisions by `requirement_id`; applied by the script on every rebuild. Edit this file, not `requirements.csv` |
| `pinned-pairs.csv` | Deliberately chosen potential-inconsistency pairs (5 pairs, 10 rows). Always included in the sample, marked `sampling = PINNED_PAIR`, and `related_requirement_ids` points to the partner |
| `review-notes.md` | Row-by-row review: rows to replace before freezing v0.1, how the guide's open questions were applied |
| `../annotations/annotation-template.csv` | One empty annotation row per sampled requirement (fields from plan M1.5) |

## Columns of `requirements.csv`

| Column | Meaning |
|---|---|
| `requirement_id` | `R001`… unique, ordered by document and position |
| `source_document` | XML file name in `data/raw/XMLZIPFile` |
| `source_section` | Section number and title in the source document (empty if the source has none) |
| `source_req_id` | Original requirement ID in the source (`<req id>`, `REQ-n`, `[SSSnnn]`), empty if none |
| `requirement_text` | Original wording; only whitespace is collapsed, PDF ligatures expanded and ID labels removed |
| `context_before` / `context_after` | Previous / next text unit in the **same section** (max 300 chars) |
| `related_requirement_ids` | Other sampled requirements taken from the same section (`;`-separated), so that potential inconsistency can be checked |
| `target_diagram` | `USE_CASE` / `CLASS` / `SEQUENCE`, **heuristic draft, must be reviewed** (see below) |
| `source_type` | `REAL` for every row (no synthetic data in this file) |
| `sampling` | `RANDOM` (drawn by the seeded sampler) or `PINNED_PAIR` (chosen on purpose from `pinned-pairs.csv`). Report results with and without pinned rows |

## How candidates were extracted

- Documents with `<req>` tags (cctns, gamma j, eirene_fun, ertms, keepass, peering): each `<req>` is one candidate.
- Other documents: sentences containing `shall / must / should / is required to / has to`; for documents with fewer than 10 such sentences (get real, video search, …) `will / can` are accepted too. TCS is split on its `[SSSnnn]` tags.
- Excluded: fewer than 5 or more than 70 words, statements about the document itself, leftover IEEE template guidance, list lead-ins whose items are elsewhere (ending with ":" or "… the following"), sentences with an absorbed heading or list label ("… accessible Reliability and availability A measure …", "Monitor level Each subsystem …"), EIRENE informative clauses `(I)`, introductory sections (purpose, scope, references, user classes, …), and duplicates within a document.
- Cleaned without changing wording: leading all-caps headings, trailing EIRENE sub-headings after the (M)/(O) marker, ID labels. Sentences are not split inside straight double quotes.

## Sampling

Deterministic: each document gets its own generator seeded from `392` + document name, so changing one document never alters the sample of another. Quota is 7–8 per document (120 total), so no single domain dominates (eirene_fun alone holds ~15% of all candidates). Inside a document, runs of 1–3 consecutive requirements from the same section are drawn; 59/120 rows belong to such clusters. Length: 6–59 words, median 20.

Excluded from sampling (`EXCLUDED_DOCS` in the script): `2008 - peering.xml` (use-case pre/post-conditions, not requirements), `2007 - get real 0.2.xml` (informal student document) and `2009 - peppol approved.xml` (legal/organisational analysis). Texts used in `data/fixtures/smoke.csv` are excluded as well.

**Pinned pairs.** Random sampling of PURE sentences yields almost no potential-inconsistency cases (0 of 120 in sample 2), so 5 pairs were selected by hand from `candidates-all.csv` and listed in `pinned-pairs.csv`. They count toward their document's quota, are marked `sampling = PINNED_PAIR`, and must be disclosed in the experiment protocol: Gate detection metrics should be reported for the random subset and for the full set.

## Known limitations (Member 1 to review before freezing v0.1)

1. **`target_diagram` starts as a keyword heuristic** (interaction verbs → SEQUENCE, data/structure verbs → CLASS, otherwise USE_CASE) and is corrected row by row in `target-diagram-overrides.csv` (36 rows so far; split 81 USE_CASE / 22 CLASS / 17 SEQUENCE). It stays skewed because most PURE sentences are capability statements.
2. Many sampled rows are non-functional or project constraints (performance, platform, legal). They are real, but some have no meaningful UML target; decide whether to keep or replace them.
3. Some candidates are not requirements in the strict sense: peering `<req>`s are use-case pre/post-conditions, and get real / video search are informal student documents. Candidates are not labels: annotators decide.
4. PDF conversion errors stay in the text on purpose (e.g. "u nits", "can' mt ove"), because the original wording must not be rewritten.
